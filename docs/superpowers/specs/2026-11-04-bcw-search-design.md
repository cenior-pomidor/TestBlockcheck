Дата: 2026-11-04
Статус: на согласовании
Репозиторий: `cenior-pomidor/TestBlockcheck`, ветка `claude/serene-fermi-x2t6l3`
Предыдущие этапы: `2026-10-31-bcw-android-engine-design.md` (поиск `bcw`, PR #1),
`2026-11-01-bcw-module-design.md` (модуль обхода, PR #2, релиз `v0.1.0`)

## 1. Цель

Вкладка «Поиск» в WebUI модуля: одной кнопкой подобрать стратегию для текущей сети, собрать из неё
пресет, назначить его сети, проверить через сам обход и откатить, если сайты не открываются.
Поиск идёт рядом с включённым обходом и не прерывает его (изоляция по меткам — этап 1).

Этап 3 готов, когда на МегаФоне (где `default` не открывает YouTube) поиск из WebUI за ≤ 5 минут
находит, применяет и проверяет стратегию, после чего YouTube-видео открывается.

### 1.1. Решения владельца

| Вопрос | Решение |
|---|---|
| Что проверять | готовый набор доменов, который можно дополнить или изменить; YouTube — отдельной группой |
| Что делать с найденным | применять автоматически, проверять через обход, при провале откатывать |
| Основа пресета | выбирается перед запуском, по умолчанию — текущая стратегия сети |
| Время одного поиска | до ~5 минут |
| Архитектура | фоновое задание в Rust (`bcw search run`) под управлением `bcw ctl search …`; служба `bcw svc` не меняется |

### 1.2. Не входит

QUIC/UDP (поиск их не перебирает — спека этапа 1, §«Не входит»), IPv6, автоматическая проверка
настоящих серверов видео `rr…---sn-….googlevideo.com`, поиск на роутере.

## 3. Набор доменов

Два списка в `/data/adb/bcw/lists/`, умолчания — в `module/defaults/lists/`. Правятся из вкладки
«Поиск» существующими `ctl list get|set`: имена `search-general` и `search-youtube` добавляются
к допустимым (`LIST_NAMES`, `engine/src/bypass/store.rs:14`), но вкладка «Списки» их не
показывает.

| Список | Умолчание |
|---|---|
| `search-general.list` («Общие») | `rutracker.org`, `discord.com`, `x.com`, `instagram.com` |
| `search-youtube.list` («YouTube») | `www.youtube.com`, `i.ytimg.com`, `redirector.googlevideo.com` |

Домены, которые не заблокированы или заблокированы по IP / не отвечают (`NotBlocked`, `IpBlocked`,
`SynBlocked`, `HostDead`, `DnsFailed`), пропускаются: подмена пакетов им не поможет. Перебираются
`SniBlocked` и `Throttled`.

## 4. Ход поиска

Все шаги выполняет задание `bcw search run`, всегда с 254 воркерами. Время — оценка (U4).

1. **Подготовка (≈5 с).** У службы через сокет `bcw.svc` берутся ключ и имя сети и состояние
   обхода; читаются основа, оба списка, настройки; берётся замок поиска `bcw.instance`.
   Без сети (`offline`) — отказ.
2. **Базовая проверка (≈10 с).** Каждый домен обеих групп, для TLS 1.3, TLS 1.2 и HTTP: тип
   блокировки (`BlockType::classify` и проба данных, как в `scan`). Проба несёт метку контроля и
   идёт мимо обхода.
3. **Сужение — отдельно для каждой группы.**
   - Первый заблокированный по TLS 1.3 домен группы — весь набор TLS 1.3 (≈40 с).
   - Прошедшие — на TLS 1.2 того же домена (если он заблокирован), затем на каждом следующем
     заблокированном домене группы по его заблокированным протоколам. Каждая ступень берёт
     только прошедших предыдущую.
   - Если в группе TLS 1.3 не заблокирован ни на одном домене, а TLS 1.2 заблокирован — весь
     набор TLS 1.2 (≈80 с) и дальше так же.
   - HTTP — своя цепочка по доменам, где заблокирован HTTP (≈9 с).
   - Для домена `Throttled` проба ступени — `DataTransfer` (реальная загрузка), для
     `SniBlocked` — `Standard` (HEAD).
   - Ступень, после которой не осталось стратегий, заканчивает группу с итогом «не найдено».
4. **Проверка с реальной загрузкой (≈30–60 с).** Прошедшие стратегии каждой цепочки
   упорядочиваются по простоте (F5); первые 10 проходят `check` с `passes=3` на всех
   заблокированных доменах группы.
5. **Выбор.** В каждой цепочке — лучшая по ранжированию `check` (F5) среди стратегий с полной
   доставкой хотя бы в одном проходе на каждом домене; при равенстве — проще.

Итог перебора — до трёх строк: `FOUND_YOUTUBE` (TLS, группа «YouTube»), `FOUND_TLS` (TLS,
«Общие»), `FOUND_HTTP` (HTTP, «Общие»; HTTP группы «YouTube» не перебирается).

**Ограничения:**

- Жёсткий срок шагов 2–5 — 5 минут. По сроку перебор прекращается, берётся лучшее
  подтверждённое `check`; ничего не подтверждено — итог «не найдено», ничего не применяется.
- `ctl search stop` на шагах 1–5 — остановка, ничего не применяется.
- Перед применением ключ сети сверяется со службой; другой — итог «сеть сменилась», ничего не
  применяется.
- Обход не `running` (выключен, `paused_home`, `blocked_neighbour`, `failed`) — пресет
  сохраняется, сети не назначается, итог «сохранено, не применено: обход не запущен».

## 5. Сборка пресета

**Имя:** `found-<основа>-<ГГГГММДД-ЧЧММ>` (местное время телефона), основа обрезается так,
чтобы имя уложилось в 64 символа (F13). Совпадение имени — суффикс `-2`, `-3`, ….

**Текст:** текст основы (перекрытие из данных главнее модульного, как в `Store::preset_text`)
копируется без изменений; ключи `FOUND_*`, если в основе уже были, вычёркиваются; в конец
дописывается блок:

```
# Найдено поиском bcw <дата время>, сеть «<имя сети>», основа <имя>
FOUND_YOUTUBE="<строка или пусто>"
FOUND_TLS="<строка или пусто>"
FOUND_HTTP="<строка или пусто>"
```

**Профили.** Парсер пресетов знает три новых ключа; сборщик аргументов (`bypass/args.rs`) делает
из каждого непустого ключа отдельный профиль (через `--new`), так что `--out-range` и
`--payload=` найденного не задевают части основы (F15). Новый порядок:

1. звонки (как было);
2. `FOUND_YOUTUBE`: `--filter-tcp=443 --filter-l7=tls --hostlist=$LISTS_DIR/youtube.list
   --hostlist-exclude=$LISTS_DIR/exclude.list <строка>`;
3. `NFQWS_ARGS_CUSTOM` (как было);
4. UDP, QUIC (как было);
5. `FOUND_TLS`: `--filter-tcp=443 --filter-l7=tls <строка>` — вариант с ipset и вариант с режимом
   списков, как у `NFQWS_ARGS`;
6. `FOUND_HTTP`: `--filter-tcp=80 --filter-l7=http <строка>` — так же;
7. `NFQWS_ARGS` (как было) — то, что поиск не проверял (например, `mtproto`, порты 1984/5222), и
   запасной путь.

Пресеты без `FOUND_*` собираются в точности как в `v0.1.0` (тест на все 28 пресетов).

Строки `FOUND_*` проверяются при сохранении: только токены, начинающиеся с `--`, без `--new`,
`--filter-*`, `--hostlist*`, `--ipset*`, `--qnum`, `--user`, `--debug`, `--lua-init`.

Редактор вкладки «Стратегии» показывает и сохраняет ключи `FOUND_*` вместе с шестью прежними.

## 6. Применение, проверка, откат

1. **Перед запуском** WebUI проверяет `NET_STRATEGY`. При `0` — вопрос: «Чтобы назначить
   найденное этой сети, нужно включить стратегии по сетям. Сети с сохранённой стратегией начнут
   её использовать. Включить?» Да — `search start --enable-net-strategy`; нет — поиск не
   запускается.
2. **Журнал отмены.** До любых изменений в `runs/<id>/undo.json` записываются: прежняя запись
   сети в `networks.tsv` (или её отсутствие), прежнее `NET_STRATEGY`, имя нового пресета,
   строки, которые будут добавлены в `user.list`.
3. **Применение:** сохранить пресет; при режиме `list`/`auto` добавить в `user.list`
   заблокированные домены группы «Общие», которых там нет (F11); при `--enable-net-strategy`
   поставить `NET_STRATEGY=1`; записать сеть → пресет (как `ctl strategy apply --network`);
   уведомить службу. Ждать до 20 с, пока служба не станет `running` с новой стратегией. Откат
   службы к `last_good` (nfqws2 упал) или срок — провал.
4. **Проверка (≈10–20 с).** Каждый домен, заблокированный на шаге 2 §4, — через обход (без
   метки, как F12), по каждому его заблокированному протоколу (TLS 1.3, TLS 1.2, HTTP), 2 попытки,
   успех — получено ≥ 32 КБ (`DATA_TRANSFER_MIN_BYTES`, порог `check`). Группа прошла, если
   прошли все её домены.
5. **Итог:**
   - обе группы прошли (или прошла единственная непустая) — «применено и проверено»;
   - одна прошла, другая нет — ключи `FOUND_*` провалившейся группы очищаются, пресет
     пересохраняется, служба перезапускается, прошедшая группа проверяется ещё раз; прошла —
     «применено частично» с указанием, что не подошло; нет — полный откат;
   - иначе — полный откат.
6. **Полный откат** по `undo.json`: прежняя запись сети (или удаление), удаление пресета
   `found-…`, удаление добавленных строк `user.list` (только их), прежнее `NET_STRATEGY`,
   уведомление службы. Найденные строки остаются в отчёте.
7. `ctl search stop` на шагах 3–5 — полный откат.
8. **Обрыв посреди применения** (перезагрузка, `SIGKILL`): `search status` и `search start`, не
   найдя живого задания при `undo.json` без отметки завершения, делают полный откат и сообщают
   об этом. Служба `bcw svc` в этом не участвует.

После «применено» WebUI просит открыть видео в YouTube: серверы видео автоматически не
проверяются (U1).

## 7. Интерфейс

### 7.1. Команды `bcw ctl search` (JSON, `schema: 1`, только root)

| Команда | Что делает |
|---|---|
| `search start [--base <пресет>] [--enable-net-strategy]` | запускает `bcw search run` в своей сессии (`setsid`), вывод — `runs/<id>/job.log`; сразу отвечает `{id}`. Отказ: поиск уже идёт, нет сети, нет основы |
| `search status` | состояние последнего задания из `runs/<id>/state.json`: шаг, сделано/всего, секунды из 300, по доменам — тип блокировки и сколько стратегий осталось, итог; доводит прерванный откат (§6.8) |
| `search stop` | `SIGTERM` группе задания; ответ после выхода задания (до 30 с) |
| `search runs` | последние 10 отчётов: id, время, сеть, итог |
| `search report <id>` | отчёт целиком |

`id` — `ГГГГММДД-ЧЧММСС`. Хранится 10 последних каталогов `runs/<id>/`; старые удаляет
`search start`. `state.json` пишется атомарно (временный файл + `rename`). Аргументы WebUI — в
`commands.js`, значения после `--`; разбор проверяет `webui_argv_parses`.

### 7.2. Вкладка «Поиск»

- Вверху — сеть и состояние обхода; выбор основы (умолчание — стратегия этой сети, иначе
  `DEFAULT_STRATEGY`); предупреждение про `NET_STRATEGY`.
- Поля «Общие» и «YouTube» с кнопками «Сохранить» и «По умолчанию».
- «Найти» / «Стоп».
- Ход: шаг, полоса перебора, время из 5:00, строки по доменам.
- Итог: одно из «применено и проверено», «применено частично», «откат», «не найдено»,
  «остановлено», «сеть сменилась», «сохранено, не применено»; найденные строки (копируются);
  цифры `check`; таблица проверки; просьба открыть видео.
- История — 10 последних поисков, нажатие открывает отчёт.
- Во время поиска — `search status` раз в секунду; при открытии вкладки — один раз.

## 8. Тесты и приёмка

Сначала падающий тест, потом правка. Тесты работают только во временных каталогах и с
поддельными службой, `iptables` и прибором проб; реальные системные пути не трогаются.

**Rust:**
- сборка аргументов: порядок профилей с `FOUND_*`, ipset и режим списков, пустые ключи; все
  28 пресетов без `FOUND_*` дают те же аргументы, что в `v0.1.0`;
- проверка строк `FOUND_*` (§5);
- сборка текста пресета: основа без изменений, замена прежних `FOUND_*`, имя и суффиксы;
- сужение на поддельном приборе: порядок ступеней, пропуск незаблокированных, `Throttled` →
  `DataTransfer`, пустая ступень;
- выбор лучшей; срок 5 минут → лучшее подтверждённое;
- применение, проверка и откат: все исходы §6.5, точность правок `user.list`, возврат
  `NET_STRATEGY`, смена сети, обход не `running`, `stop` на каждом шаге, доведение отката по
  `undo.json`;
- `ctl search`: разбор аргументов, образцы ответов в `module/tests/ctl-samples/`.

**WebUI:** `test_search.mjs` — отображение шагов и итогов по образцам; новые команды — в
`test_commands.mjs`.

**Приёмка на телефоне** (шаги — в `module/README.md`):
1. МегаФон, основа `default`: поиск из WebUI укладывается в 5 минут, итог «применено и
   проверено», YouTube-видео открывается (U1, U2, U4).
2. Закрыть WebUI во время поиска, открыть снова — поиск идёт или закончился, итог виден (U3).
3. «Стоп» во время перебора — ничего не применено.
4. Переключиться на Wi-Fi во время поиска — «сеть сменилась».
5. Откат: сценарий выбирается в плане; основная проверка отката — тестами.
6. Обход и поиск рядом: обход не прерывается, дублей правил нет.

**Выпуск:** `v0.2.0` после приёмки и независимого обзора кода.
