# Этап 1. Движок поиска стратегий `bcw` для Android — дизайн

Дата: 2026-10-31
Статус: на согласовании
Репозиторий: `cenior-pomidor/TestBlockcheck`

## 1. Контекст и цель продукта

Итоговый продукт — модуль KernelSU с WebUI для Android, который объединяет:

- **обход DPI** — форк [nfqws2-android](https://github.com/dea1hwatcher/nfqws2-android)
  (MIT), урезанный до нужных функций;
- **поиск рабочих стратегий** — порт [blockcheckw](https://github.com/rcd27/blockcheckw)
  (MIT, версия 0.12.1, коммит `9ac1485`), найденная стратегия сразу становится
  стратегией обхода для текущей сети.

Работа разбита на три этапа, у каждого своя спецификация, план и согласование:

1. **Движок поиска `bcw` на Android** (этот документ) — CLI, проверяется на телефоне
   до форка. Несёт главный технический риск: метки, iptables, скорость.
2. **Урезанный форк обхода** — из nfqws2-android.
3. **Вкладка «Поиск» и связка** — результат поиска становится стратегией сети.

### 1.1. Решения, принятые с владельцем

| Вопрос | Решение |
|---|---|
| Оболочка | модуль KernelSU с WebUI (как у nfqws2-android) |
| Основа продукта | форк nfqws2-android + `bcw` |
| Функции форка (этап 2) | применение стратегий; стратегии по сетям; пауза в домашнем Wi-Fi; автозапуск и сторож; готовые пресеты и редактор; блокировка QUIC; списки доменов (свой, авто, исключения, ipset); журналы со статистикой; обновления модуля из менеджера |
| Не берём | VPN-пауза, пауза при «белых списках», фильтр приложений, раздача, IPv6, умный режим, каталоги, резервная копия, проверки DPI/DNS/Telegram, темы и выбор языка |
| Сосуществование поиска и обхода | **изоляция**: обход работает во время скана, пробы идут мимо его цепочек |

Ранние решения про выгрузку в каталоги и пресеты nfqws2-android и magisk-zapret2
отменены: в объединённом приложении стратегии остаются внутри приложения.

### 1.2. Факты об устройстве владельца

Получены командами на телефоне (Google Pixel 9 Pro, Android 17, KernelSU):

- `# CONFIG_NF_TABLES is not set` — **nftables в ядре нет**, только iptables (legacy).
- `CONFIG_NETFILTER_XT_TARGET_NFQUEUE=y`, `CONFIG_NETFILTER_XT_MATCH_CONNBYTES=y`.
- `ip rule`: маршрут «сеть по умолчанию» —
  `31000: from all fwmark 0x0/0xffff iif lo lookup wlan0`, в конце
  `32000: from all unreachable`. Сокет с ненулевыми младшими 16 битами метки,
  которые не совпадают с номером реальной сети (здесь `0xa7`), до правила
  31000 не доходит.

Из исходников:

- Android netd, `include/Fwmark.h`: биты 0–15 — `netId`, 16 — `explicitlySelected`,
  17 — `protectedFromVpn`, 18–19 — `permission`, 20 — `uidBillingDone`,
  21–30 — `reserved`, 31 — `ingress_cpu_wakeup`.
- blockcheckw держит номер профиля в битах 0–15 (`PROFILE_MASK = 0xFFFF`,
  `src/nfqws2/space.rs`) — на Android это поле netd, поэтому раскладку нужно менять.
- nfqws2 сравнивает `(fwmark & filter_mark_mask) != filter_mark`
  (`nfq2/desync.c:233` в zapret2) — маска профиля может быть любой.
- nfqws2-android собирает nfqws2 из zapret2 `v1.0.5.2`
  (`.github/scripts/build-android-binaries.sh`); `--filter-mark` есть с v1.0.5.
- Метки nfqws2-android (`lib/common.sh`): `0x40000000` — пакеты его nfqws2
  (`MARK_PROCESSED`); `0x20000000` / `0x10000000` — метки соединений фильтра
  приложений; `0x0f000000` и `0x000f0000` — счётчики пакетов в метке соединения,
  только когда в ядре нет `connbytes`. Очередь по умолчанию — `300`.
- magisk-zapret2: `qnum=200`, `desync_mark=0x40000000`.

## 2. Цель и границы этапа 1

**Цель:** `bcw` — статический бинарник для arm64, который на телефоне под root
выполняет `doctor`, `benchmark`, `scan`, `check` (а также `status`, `universal`)
поверх iptables, не мешая работающему модулю обхода.

**Входит:**

- бэкенд iptables вместо nftables;
- новая раскладка метки, совместимая с Android netd и модулями обхода;
- поведение «встроенного режима» по умолчанию;
- настраиваемые пути к nfqws2 и Lua, DoH с настраиваемым резолвером;
- подкоманда `doctor`;
- CI: тесты, интеграционный тест на iptables, сборка arm64.

**Не входит:** WebUI, модуль KernelSU, форк обхода (этапы 2–3); IPv6; QUIC/UDP;
32-битные ARM и x86; Magisk-специфика.

## 3. Карта битов метки

| Биты | Владелец | Значение |
|---|---|---|
| 0–20 | Android netd | в наших пробах всегда `0` |
| 21 | bcw | `DESYNC` = `0x00200000` — пакеты, отправленные nfqws2 поиска (`--fwmark`) |
| 22–29 | bcw | `PROFILE` = `0x3FC00000`, номер стратегии `1…254`; `255` — `CONTROL` |
| 30 | модули обхода | пакеты nfqws2 обхода — не трогаем |
| 31 | Android netd | не трогаем |

Производные значения:

- `OUR_MASK = DESYNC | PROFILE = 0x3FE00000`;
- метка пробы стратегии `N` = `N << 22`;
- метка пробы контроля и DoH = `255 << 22 = 0x3FC00000`;
- аргумент профиля движка: `--filter-mark=<N<<22>/0x3FC00000`;
- потолок `--profiles-per-instance` и `--workers` — **254**.

Инварианты (проверяются тестами):

- никакая метка пробы не задевает биты 0–20, 30, 31;
- `DESYNC` не встречается в метке пробы (иначе nfqws2 пропускает пакет без обработки);
- правила меняют в метке соединения только биты 21–29.

Реализация: `PROFILE_MASK`-константа в `nfqws2/space.rs` заменяется на
`MarkSpace { profile_shift: 22, profile_width: 8, desync: 0x00200000, control: 255 }`;
`ProfileMark::so_mark()`, `filter_arg()`, `restore_mask()` выводятся из него.
Ключи `--mark-base`, `--desync-mark` заменяются ключами раскладки
(`--mark-profile-shift`, `--mark-desync`) с проверкой инвариантов при разборе.

## 4. Правила iptables

Применение — `iptables-restore --noflush -w`, по одной транзакции на таблицу.
Объявление цепочки `:bcw_x - [0:0]` в режиме `--noflush` создаёт или очищает её.
Свои цепочки, переход на каждую — **первой строкой** стандартной цепочки.

### 4.1. Статическая часть (на весь прогон)

`*raw`:

```
:bcw_raw - [0:0]
-I OUTPUT 1 -j bcw_raw
-A bcw_raw -m mark --mark 0x00200000/0x00200000 -j CT --notrack
```

**Признак «наше соединение» в метке соединения — только бит 21.** Биты 22–29 метки
соединения несут номер стратегии, но опознавать по ним нельзя: nfqws2-android может
держать в метке соединения биты 24–29 (счётчики, фильтр приложений), бит 21 он не
использует. В метке *пакета* биты 21–29 чужой трафик не несёт (netd — 0–20,
nfqws2 обхода — 30).

`*mangle`:

```
:bcw_out  - [0:0]
:bcw_post - [0:0]
:bcw_pre  - [0:0]
:bcw_q    - [0:0]
:bcw_qin  - [0:0]
:bcw_ctl  - [0:0]
-I OUTPUT 1      -j bcw_out
-I POSTROUTING 1 -j bcw_post
-I PREROUTING 1  -j bcw_pre

# OUTPUT: всё с нашими битами минует остальные цепочки mangle OUTPUT (в т.ч. обход)
-A bcw_out -m mark ! --mark 0x0/0x3FE00000 -j ACCEPT

# POSTROUTING, базовая часть (без диспетчеризации)
-A bcw_post -m mark --mark 0x00200000/0x00200000 -j ACCEPT
-A bcw_post -m mark --mark 0x3FC00000/0x3FC00000 -j bcw_ctl
-A bcw_post -m mark ! --mark 0x0/0x3FE00000 -j ACCEPT

# PREROUTING, базовая часть
-A bcw_pre -p icmp --icmp-type time-exceeded -m connmark --mark 0x00200000/0x00200000 -j DROP
-A bcw_pre -p icmp --icmp-type time-exceeded -m conntrack --ctstate INVALID -j DROP
-A bcw_pre -m connmark --mark 0x00200000/0x00200000 -j ACCEPT

# контрольное соединение: пометить нашим (бит 21) с номером 255, без очереди
-A bcw_ctl -j CONNMARK --save-mark --nfmask 0x3FC00000 --ctmask 0x3FC00000
-A bcw_ctl -j CONNMARK --set-xmark 0x00200000/0x00200000
-A bcw_ctl -j ACCEPT

# очередь исходящих: номер стратегии в метку соединения, бит 21, nfqws2 поиска
-A bcw_q -j CONNMARK --save-mark --nfmask 0x3FC00000 --ctmask 0x3FC00000
-A bcw_q -j CONNMARK --set-xmark 0x00200000/0x00200000
-A bcw_q -j NFQUEUE --queue-num <Q>

# очередь входящих SYN/ACK: восстановить номер стратегии (нужно autottl)
-A bcw_qin -j CONNMARK --restore-mark --nfmask 0x3FC00000 --ctmask 0x3FC00000
-A bcw_qin -j NFQUEUE --queue-num <Q>
```

Нет `--queue-bypass`: если nfqws2 поиска упал, теряются только наши пробы
(«откажи закрыто»), трафик пользователя в эту очередь не попадает.

### 4.2. Диспетчеризация (на каждый план)

Одна транзакция `*mangle` объявляет `bcw_post` и `bcw_pre` заново (это их очищает)
и собирает каждую как базовую часть с правилами плана **перед** завершающими
ACCEPT:

```
# bcw_post: после правила DESYNC → ACCEPT, по строке на каждый IP цели
-A bcw_post -p tcp --dport <PORT> -d <IP>
            -m mark ! --mark 0x0/0x3FC00000
            -m mark ! --mark 0x3FC00000/0x3FC00000
            -m connbytes --connbytes 1:10 --connbytes-dir original --connbytes-mode packets
            -j bcw_q

# bcw_pre: после двух ICMP-правил, по строке на каждый IP цели
-A bcw_pre -p tcp --sport <PORT> -s <IP> --tcp-flags SYN,ACK SYN,ACK
           -m connmark --mark 0x00200000/0x00200000
           -m connmark ! --mark 0x3FC00000/0x3FC00000
           -j bcw_qin
```

Снятие диспетчеризации — та же транзакция с одной базовой частью.

Перенос сделан один в один с правилами оригинала (`src/firewall/nftables.rs`):
лимит первых 10 исходящих пакетов (#68), восстановление метки для SYN/ACK, отбрасывание
ICMP time-exceeded. Правило `ctstate INVALID` для ICMP действует на весь трафик —
как в оригинале, но только на время прогона.

Номер очереди `<Q>` по умолчанию **777** (не 200 и не 300, занятые
magisk-zapret2 и nfqws2-android). Занятая очередь — существующий исход `queue_busy`
(код выхода 7).

### 4.3. Страж порядка

Перед каждым планом `bcw` читает `iptables -w -t mangle -S OUTPUT|POSTROUTING|PREROUTING`
и `-t raw -S OUTPUT`. Если первым правилом стоит не переход на нашу цепочку,
переход удаляется и вставляется снова на позицию 1, факт пишется в поток `--progress`
событием `{"event":"reorder","chain":…}`. Если цепочка исчезла (система сбросила
правила), статическая часть применяется заново.

### 4.4. Уборка

При выходе, по сигналу и при старте (остатки от `SIGKILL`): цикл
`iptables -w -t <t> -D <CHAIN> -j <bcw_x>` пока удаётся, затем `-F` и `-X` своих
цепочек. Идемпотентно, ошибки «нет такого правила» не считаются отказом.

### 4.5. Код

- `firewall/nft.rs`, `firewall/nftables.rs` заменяются на `firewall/ipt.rs`
  (единственная точка вызова `iptables`/`iptables-restore`, типизированный
  батч на таблицу — как `NftBatch`) и `firewall/rules.rs` (сборка правил выше).
- Тип `OwnedTable` становится `OwnedChains`: создать, применить диспетчеризацию,
  снять диспетчеризацию, снести; хэндл не `Clone`, снос потребляет его.
- Валидация IP до подстановки в правила сохраняется (`validate_ip_set`).

## 5. Остальные изменения движка

1. **Встроенный режим по умолчанию.** Android-сборка всегда ведёт себя как
   `--embedded` оригинала: чужие правила и процессы nfqws2 не трогаются (о них
   сообщается событием `neighbours`); контроль идёт с собственной меткой (`CONTROL`);
   вопросов нет; своя группа процессов; свои остатки снимаются при входе; память
   прошлых запусков (`config.json`) не читается и не пишется; системный резолвер
   запрещён.
2. **Пути.** `--nfqws2 <путь>` и `--lua-dir <путь>` вместо зашитого `/opt/zapret2`.
   По умолчанию на этапе 1 — `/data/adb/modules/nfqws2-android/bin/nfqws2` и
   `/data/adb/modules/nfqws2-android/lua`. Рабочий каталог и отчёты —
   `--work-dir`, по умолчанию `/data/adb/bcw/` (отчёты в `runs/<дата-время>/`).
3. **Пользователь nfqws2** — `--uid=0:0` (в Android нет `nobody` в `/etc/passwd`;
   nfqws2-android по умолчанию тоже запускает nfqws2 от root).
4. **DNS.** Только DoH собственным сокетом с меткой `CONTROL`. Встроенные резолверы
   оригинала — 1.1.1.1, 8.8.8.8, 9.9.9.9 (IP-литералы); добавляется
   `--doh <ip>[:<host>]` (можно несколько) для своего резолвера.
5. **Отключено:** `--via`, `--alive-via` (маршруты `ip route` Android игнорирует
   из-за policy routing); `--upgrade` и проверка обновлений; `completions`;
   остановка и запуск службы zapret2.
6. **Подкоманда `doctor`** — JSON в stdout (схема версионируется), человеку —
   таблица в stderr. Проверки:
   - запущено от root;
   - `/proc/config.gz`: `NETFILTER_XT_TARGET_NFQUEUE`, `NETFILTER_XT_MATCH_CONNBYTES`,
     `NETFILTER_XT_TARGET_CONNMARK`, `NETFILTER_XT_MATCH_CONNMARK`,
     `NETFILTER_XT_TARGET_CT`, `IP_NF_MANGLE`, `IP_NF_RAW` (если файла нет —
     «неизвестно», не провал);
   - есть `iptables` и `iptables-restore`, проба `iptables-restore --test` на
     статической части;
   - nfqws2 по пути запускается и в справке есть `--filter-mark`;
     Lua-файлы `zapret-lib.lua`, `zapret-antidpi.lua` на месте;
   - **маршрут метки:** TCP-коннект на 443 к каждому DoH-резолверу с меткой
     `CONTROL` и с меткой стратегии `1` (без правил bcw) — оба должны соединиться;
   - доступность DoH: запрос `A` хотя бы через один резолвер;
   - соседи: чужие цепочки mangle с `NFQUEUE`, процессы nfqws2, занятые очереди
     (`/proc/net/netfilter/nfnetlink_queue`).
7. **Сборка** — `aarch64-unknown-linux-musl`, статически, без UPX.
8. **Без изменений:** корпус стратегий (13 943), логика `scan`/`check`, формат
   JSON-отчёта (поле `schema` повышается, если меняется `run`), ключи `--stream` и
   `--progress`, команды `benchmark`, `status`, `universal`.

## 6. Ожидаемая скорость

README оригинала: ~2 мин на TLS 1.2 и ~150 стратегий/с при 1024 воркерах; железо
замера не указано. На Android воркеров не больше 254. Если скорость растёт линейно
с числом воркеров (допущение), выходит ~37 стратегий/с: ~4 мин на TLS 1.2,
~6–7 мин на весь корпус, плюс ~55 перезапусков nfqws2 вместо ~15. Реальная цифра —
по `bcw benchmark` на телефоне. `check` упирается в линию, а не в устройство.

| # | Допущение / риск | Как проверяем / что делаем |
|---|---|---|
| R1 | ACCEPT в mangle пропускает и цепочки самого Android (учёт трафика, idletimer) для наших проб — для коротких тестовых соединений безвредно | прогон на телефоне, сравнение `iptables-save` до/после, работа сети после |

## 8. Проверка

### 8.1. CI (GitHub Actions, без телефона)

- `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` — тесты оригинала,
  кроме nft-специфичных, которые заменяются аналогами для iptables.
- Тесты правил с записывающим исполнителем (как `RecordingNft`):
  - статическая часть — ровно одна транзакция на таблицу;
  - переходы вставляются на позицию 1;
  - диспетчеризация — по строке на IP, лимит `connbytes 1:10`;
  - все маски — подмножество `0x3FE00000`;
  - «наше соединение» в метке соединения проверяется только по биту 21;
  - контрольная проба (`255`) не попадает в очередь;
  - мусорный IP не доходит до iptables.
- Тесты раскладки: для всех `N` в `1…254` — `so_mark & 0xC01FFFFF == 0`,
  `so_mark & DESYNC == 0`, `filter_arg` = `--filter-mark=<N<<22>/0x3FC00000`;
  `CONTROL` не совпадает ни с одной стратегией.
- Интеграционный тест: привилегированный контейнер, `iptables-legacy`,
  `nfnetlink_queue`, nfqws2 из zapret2 (подмодуль) — переделанный `e2e_infra`:
  правила ставятся, пакеты с меткой стратегии доходят до очереди, уборка оставляет
  `iptables-save` как до.
- Сборка `bcw` под `aarch64-unknown-linux-musl` на каждый push, артефакт в Actions.

### 8.2. На телефоне (выполняет владелец, присылает вывод)

1. `su -c '/data/local/tmp/bcw doctor'` — все проверки зелёные.
2. `su -c '/data/local/tmp/bcw benchmark -t 15'` — скорость.
3. На домашнем Wi-Fi, затем на мобильной сети, с включённым nfqws2-android:
   `bcw -w <N> scan -d rutracker.org -p tls12 | bcw check -d rutracker.org --take 3`;
   во время прогона обход на телефоне продолжает работать.
4. После прогона `iptables-save -t mangle` и `-t raw` не содержат `bcw_`.
5. `kill -9` посреди прогона, повторный запуск — остатки сняты при старте.

### 8.3. Критерии готовности этапа 1

- `doctor` проходит на телефоне владельца;
- прогоны из 8.2.3 заканчиваются исходом `found`, `nothing_works` или `not_blocked`,
  а не `broken`;
- после обычного выхода и после `kill -9` + перезапуска правил `bcw_` нет;
- обход nfqws2-android работает во время скана;
- скорость замерена и записана в `engine/README.md`.

Найдутся ли рабочие стратегии — свойство линии, а не критерий.

## 9. Устройство репозитория

```
TestBlockcheck/
├── engine/                 # форк blockcheckw 0.12.1 (Rust), LICENSE (MIT, rcd27)
│   ├── UPSTREAM.md         # базовый коммит 9ac1485 и список отличий
│   └── reference/zapret2   # подмодуль для интеграционного теста
├── docs/superpowers/specs/ # спецификации этапов
└── .github/workflows/      # CI движка
```

Код оригинала ложится в `engine/` отдельным коммитом без изменений, правки —
следующими коммитами, чтобы отличия от upstream были видны в истории. На этапе 2
форк nfqws2-android ляжет в корень репозитория рядом с `engine/`.
